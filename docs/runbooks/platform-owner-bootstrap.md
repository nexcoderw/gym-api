# First Platform Owner Bootstrap

## Purpose and security boundary

This runbook provisions exactly one initial NEXCODE platform owner through a local interactive CLI.
The CLI creates a standalone Nest application context and never opens a network listener. The API has
no owner-registration or bootstrap endpoint, and normal startup never invokes this workflow.

Only an authorized operator using a dedicated least-privilege PostgreSQL role may run these commands.
Do not use a PostgreSQL superuser, a production API runtime role with broader access, or a shell that
records terminal output. The terminal displays the TOTP enrollment secret and recovery codes once.

## Release prerequisites

1. Verify that the exact installed `@nexcoderw/gym-db` version exports the Step 4 authentication
   models. The source package currently reports `0.1.1`; the API lockfile must be generated by the
   developer from an approved immutable package or the reviewed local package link.
2. Deploy `20261012235203_platform_auth_persistence` using the database repository's migration
   procedure. The CLI never runs migrations.
3. Use a dedicated Neon connection and role limited to the identity, role, permission, MFA, and
   recovery-code tables needed by this operation. Prefer the direct Neon connection for this operator
   transaction if the approved role permits it.
4. Back up and confirm the target branch. Never use automated-test credentials or a production runtime
   account.
5. Perform an independent mailbox challenge with the owner. A typed email address is not evidence of
   mailbox ownership. The operator must send a one-time challenge through an approved channel and
   confirm the response outside this CLI before activation.

## Temporary operator environment

Supply secrets through the approved secret manager or an ignored, mode-`600` operator environment.
Never put credentials in command arguments, Git, tickets, screenshots, or shell history.

```dotenv
NODE_ENV=production
DATABASE_URL=postgresql://dedicated-bootstrap-role:managed-secret@exact-neon-host/neondb?sslmode=verify-full
PLATFORM_AUTH_DUMMY_PASSWORD_HASH=managed-approved-argon2id-dummy-hash
PLATFORM_AUTH_TOKEN_PEPPER=managed-canonical-base64-32-byte-key
PLATFORM_TOTP_KEYRING=production-v1=managed-canonical-base64-32-byte-key
PLATFORM_TOTP_ACTIVE_KEY_ID=production-v1
PLATFORM_OWNER_BOOTSTRAP_ENABLED=true
PLATFORM_OWNER_BOOTSTRAP_EXPECTED_DATABASE_HOST=exact-neon-host
PLATFORM_OWNER_BOOTSTRAP_EXPECTED_DATABASE_NAME=neondb
```

All other required production variables must remain valid. Environment validation compares the URL's
actual hostname and database name with the explicit fingerprint before the CLI can start. It never
prints the connection URL, username, password, keyring, or token pepper.

## Stage A: initialize the pending owner

Build the reviewed source, then start initialization from `api/api`:

```bash
npm run build
npm run bootstrap:platform-owner:init
```

The operator must type the exact target confirmation and authorization phrases. The CLI then requests
the email, display name, and password interactively. Password input is not echoed and is never accepted
as a command argument.

Initialization obtains a transaction-scoped PostgreSQL advisory lock and refuses to continue if any
platform staff identity already exists or if the email belongs to an existing user. It creates pending
`User` and `PlatformStaff` records, an Argon2id password credential, the system-owned
`platform.owner` role, only the reviewed `platform.dashboard.read` permission, and an unverified
AES-256-GCM TOTP credential. All writes roll back together on failure.

Enroll the displayed `otpauth://` URI or manual Base32 secret immediately in the owner's authenticator.
Do not copy it into notes, chat, source files, logs, or screenshots. Re-running initialization never
resets the password or MFA factor; a failed or abandoned enrollment requires a separately reviewed
database recovery procedure.

## Stage B: verify and activate

Complete the independent mailbox challenge first. Then run:

```bash
npm run bootstrap:platform-owner:activate
```

The operator confirms the same database target, authorizes activation, enters the pending email and a
current six-digit authenticator code, and attests that mailbox ownership was verified independently.
The transaction rechecks the pending states, exact role and permission allowlist, and unverified TOTP
credential. It atomically consumes the TOTP time step, confirms TOTP, activates both identity records,
and stores keyed digests for ten newly generated 128-bit recovery codes.

Store the displayed recovery codes once in an approved offline secret store. The database contains
only keyed digests. Losing both the authenticator and recovery codes requires a separately designed
account-recovery process; this bootstrap intentionally cannot reset them.

## Disable and verify

Immediately set `PLATFORM_OWNER_BOOTSTRAP_ENABLED=false`, remove the dedicated bootstrap database
credential, and close the privileged operator environment. Start the API normally and verify login:

1. Submit the owner email and password to `POST /api/v1/platform/auth/login` from the exact configured
   admin Origin.
2. Submit the returned challenge, CSRF value, and a new TOTP code to
   `POST /api/v1/platform/auth/mfa/verify`.
3. Confirm `GET /api/v1/platform/auth/session` returns `platform.owner` and only the approved effective
   permissions.

Do not reuse the enrollment verification TOTP step. Wait for the next 30-second period before login.

## Failure recovery

- Target or authorization mismatch: stop and review environment configuration; do not bypass it.
- Existing platform staff or identity conflict: stop. Do not delete or overwrite the record through
  this utility.
- Initialization failure: the transaction rolls back. Confirm database state before any retry.
- Pending enrollment abandoned or secret lost: the account remains inactive. Do not rerun
  initialization or manually activate it; use a separately reviewed cleanup/recovery change.
- TOTP failure: no activation occurs. Check device time and enrollment without exposing the secret.
- Concurrent-operation error: inspect protected operational evidence and database state before retrying.
- Recovery-code output lost after successful activation: do not rerun bootstrap. A future authenticated
  recovery-code rotation workflow is required.

Operational logs are not a tamper-resistant privileged audit trail. Production release still requires
a reviewed audit mechanism, secret retention controls, Neon role verification, and human evidence of
the independent mailbox challenge.
